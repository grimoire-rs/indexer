# The CSS Theming Ruleset

Contents: [Tokens](#tokens) · [The Cascade](#the-cascade) ·
[Accessibility](#accessibility) · [Custom Properties](#custom-properties) ·
[The Public API](#the-public-api) · [The Gate](#the-gate)

Every rule carries its evidence. *Measured* means reproduced this cycle against
a real production build or Chromium 151.0.7922.34. *Spec-derived* means cited,
not run — and is stated as such rather than dressed up.

A rule whose statement carries a bold **Except:** clause is not universal. The
exception is part of the rule, not a footnote. There are six.

## Tokens

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| CSS-TOK-01 | Any appearance value — colour, spacing, radius, shadow, duration — written as a literal is a value the consumer's one override stylesheet can never reach. A value that only LOOKS tokenized in source is a literal: a Sass `$brand`/Less `@brand` interpolation, a CSS-in-JS theme value interpolated into a template, a JS expression evaluated inside `style()`/`stylex.create()`, and a Tailwind `@theme inline` alias all compile to the bare literal. **Except: email HTML**, where most clients strip `<style>` and support no custom properties, so inline literals are the contract, not the defect.<br>*Measured:* dart-sass 1.103.1 `$brand:#ff0000` → `.button{color:#ff0000}` while `--brand` survives; less 4.9.0 identical; vanilla-extract 1.21.2 and StyleX 0.19.0 both bake `120+40` into `width:160px`; Tailwind 4.3.3 `@theme inline` emits its alias zero times. | The failure with no symptom: the consumer writes a correct-looking override, nothing happens, no error, no warning, indistinguishable from a typo. One defect wearing five syntaxes. | `node scripts/literal-colours.mjs <built.css>` — see [gate.md](gate.md). It strips `var()` fallback slots and every token declaration's right-hand side before matching; the naive one-liner reports both and goes red on a compliant build. Empty output is the pass. **Colour only** — the spacing/duration half is reviewed by eye, not gated. | MUST |
| CSS-TOK-02 | A value the build resolves before the browser sees CSS cannot be overridden by any stylesheet, however well named. Never list one in a token table — the row promises an overridability that cannot exist. Confirmed instances: Tailwind v4 `--breakpoint-*`/`--container-*` and `@theme inline` aliases; Sass `$var` / Less `@var`; a JS-computed value in vanilla-extract or StyleX; Style Dictionary's `outputReferences: false` default.<br>*Measured:* `grep -c breakpoint` on a Tailwind 4.3.3 build declaring `--breakpoint-3xl` returns 0 while `3xl:p-16` compiled to `@media (width>=120rem)`. *Spec-derived:* the Style Dictionary default. | Every other rule here assumes the consumer has a hook to reach. This is the class of value where there is none, and where the token table is the thing that lies. | Grep the BUILT stylesheet for each published token's literal name. A public token must appear as a `--name:` declaration in the output. Name absent while its value appears inlined at use sites = build-resolved: remove the row, or change the build (`outputReferences: true`, plain `@theme` instead of `@theme inline`). | MUST |
| CSS-TOK-03 | A colour token declared only under the default scope and not repeated under the dark scope silently applies in dark mode pinned to its light value — and cascade layers make it WORSE, because a consumer's unlayered one-line `:root{--accent:…}` beats both your layered light block and your layered dark block. Only overriding both scopes fixes it, which makes it a documentation obligation you state to consumers. **Except: `light-dark()` themes**, where each colour has exactly ONE declaration site carrying both branches. **And except VS Code webviews**, where the host owns the vocabulary and recomputes its properties per theme change.<br>*Measured:* the parity leak reproduced with a red control; `light-dark()` follows the cascadable `color-scheme` property, not a fixed OS read — `[data-theme=light]{color-scheme:light}` flipped it to the light branch in an OS-dark context. | A rule set that sells `@layer` without naming this cost is selling a broken dark mode — and a parity check that does not know about `light-dark()` is a lint that goes red on correct code, which is how a gate gets switched off. | `node scripts/dark-parity.mjs <built.css>` — both directions, with a `light-dark(` skip and a justified allowlist. Watch the one-directional case: a build-time tree-shake can drop a token from the generated light block while a hand-written dark block keeps it — "works in dark, broken in light", which passes a dark-mode screenshot test. | MUST |
| CSS-TOK-04 | A semantic, role-named public tier is universal. A PRIMITIVE tier is justified only where a census shows a raw value is genuinely shared by two or more semantic tokens. A COMPONENT-HOOK tier is justified only where a component needs restyling the layer plus an identity attribute do not already reach — ship it for two or three components, never speculatively. Before tokenizing an existing untokenized family, run an exhaustive literal census first.<br>*Spec-derived:* design-system methodology, framework-independent. | The named failure mode of token systems is minting too many tokens too early, and a scale picked against a half-count is wrong in a way nobody notices until the second pass. | A census is a command with a count, not a reading — for colour: `grep -oE '#[0-9a-fA-F]{3,8}\|rgba?\(\|oklch\(' -r src \| sort \| uniq -c \| sort -rn`. Re-run with a multi-line-aware matcher: the first pass misses values buried inside multi-line `transition` and `box-shadow` declarations, which is exactly how a census under-counts. A new token added with no census line in the commit body is speculative. | SHOULD |
| CSS-TOK-05 | A value mathematically or perceptually derived from another token — a tint, a nested radius, a negated margin — is written as a derivation with `calc()` or `color-mix()`, never as a second hand-computed literal. A stored copy stops tracking the source the moment a consumer overrides it, so a rebrand half-applies.<br>*Spec-derived:* reasoning over `var()` resolution semantics, whose underlying mechanism the engine probe did confirm. | The difference between a rebrand fully applying and half-applying — invisible until someone actually overrides the base token and finds the derived value unchanged. | For each pair of tokens whose values are numerically or perceptually related, the derived one must contain `calc(` or `color-mix(` referencing the other. A hand-computed literal that happens to equal a derivation is the finding. | SHOULD |

## The Cascade

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| CSS-CAS-01 | "My rule loses" has at least eight causes and only two are specificity. Attribute or class scoping inflates it (Astro, Vue, Svelte, Angular Emulated, solid-styled, Stencil `scoped`). CSS Modules and Tailwind utilities inflate nothing and lose on deterministic emit order instead. StyleX at its plugin default pads to (2,1,0)–(3,1,0) with `:not(#\#)` chains. Angular and the runtime CSS-in-JS libraries append their styles to `<head>` at render time and win ties from position. Svelte DELETES a non-matching rule at compile time. Qwik never scopes in the build at all — it scopes when it renders. A shadow boundary means the two selectors never compete.<br>*Measured:* every branch, from real production builds. | The single generalisation the source doctrine got wrong. It was drawn from two attribute-scoped frameworks and does not describe six of the others; carried unmodified into a CSS-Modules, Qwik or Shadow-DOM repo it produces a confident wrong fix. | Read the compiled or SERVED rule for the element you are restyling, not the source. Find the selector verbatim in the built stylesheet. Not there at all → the cause is compile-time deletion, a runtime transform, a shadow boundary, or a runtime-injected sheet, and no selector edit helps. Then read the surface table in the index before changing anything. | MUST |
| CSS-CAS-02 | Unlayered author CSS beats layered author CSS at any specificity, position-independent, within one tree and one origin — that is the whole mechanism. So put every block you author inside exactly one `@layer` and leave the consumer's file unlayered. **Audit the page's layer landscape first**, because adding a layer can lose: any second author stylesheet you do not control and did not layer then beats you at any specificity. Layer order is order of FIRST APPEARANCE of the name — which a preprocessor's `@use`/`@forward`/`@import` order silently fixes, and which in Angular is fixed by runtime mount order.<br>*Measured:* unlayered `.a` (0,1,0) beat layered `#i.a.b` (1,2,0); order comes from the statement, not block order; re-opening a layer keeps its original position. Survives a real production build in every framework probed. VitePress 1.6.4 is the measured losing case. | It is the only mechanism evaluated — against `:where()`, `@scope`, and raising consumer specificity — that makes a consumer's rule win unconditionally rather than by luck of selector choice. The guarantee is exactly as good as your audit of what else is in the cascade. | `node scripts/outside-layers.mjs <built.css>` — brace-match every `@layer` span, ANY name, and assert the remainder is empty apart from the documented ignore list. Never a context grep, never `grep -o`. Then enumerate every layer name present; a name you did not author is a landscape you now have to reason about. | MUST |
| CSS-CAS-03 | Importance REVERSES layer order: a layered `!important` beats an unlayered `!important`. An `!important` inside your layer therefore locks every consumer out with no escape hatch, so never add one without a comment naming why. **Across a shadow boundary the whole remedy runs backwards**: an inner `!important` beats an outer `!important` AND an outer normal rule, in every combination measured. A consumer cannot out-`!important` a component from outside — they already win at normal importance by Context and lose to an inner `!important` unconditionally. Never author `!important` in a component's `:host`/`::part()`/`::slotted()` rules.<br>*Measured:* all four shadow combinations on both the `::part()` and `:host` paths; layer-order reversal at equal specificity in light DOM; an adopted sheet beat the component's layered rule but lost to its `!important`; `mode:'closed'` closed the channel. | The one place the layering mechanism inverts — and the shadow half is the worst kind of error to get backwards, since the advice is confidently actionable and permanently defeats the contract. | Search inside each built layer span for `!important`; every hit needs an adjacent justification comment and an allowlist entry. Separately grep the entry stylesheet for framework-wide important flags — `@import "tailwindcss" important;`, a trailing-`!` utility modifier: where one is present the whole unlayered-consumer-wins promise is void for every rule it touches. In a shadow-DOM component, grep the component's own styles for `!important` at all; each hit is a defect, not a fix. | MUST |
| CSS-CAS-04 | The cascade sorts Element-Attached Styles above Layers: a `style=""` attribute beats every author stylesheet rule at any specificity in any layer. Only `!important` reaches it, and inline `!important` beats that in turn. So any framework feature that paints via an inline style escapes the whole contract — a syntax highlighter, Vue's `v-bind()` in CSS, an editor host writing theme tokens onto the root element, a chart library. **Except: email HTML**, where inline styles are not an escape from the contract, they ARE the contract.<br>*Measured:* all five orderings. *Spec-derived:* the email half, cited from client support matrices — no email client is locally runnable. | The gap the source doctrine missed entirely — and the one surface where the advice inverts rather than merely not applying. | Render the page and grep the SERVED HTML for `style="` on the elements you claim are themeable. Each hit is either a value that must move into a custom property, or a documented exception whose `!important` workaround is placed outside the layer (light DOM only — see CSS-CAS-03). | MUST |
| CSS-CAS-05 | `@scope` is not a substitute for cascade layers. It contributes zero specificity of its own (a bare selector inside it behaves as `:where(:scope)`), it does not reduce the specificity of the selectors you write inside it, and its proximity tie-break only decides between rules already equal in specificity — it is outranked by layers. Two smaller traps: the limit element is EXCLUDED from the scope (the donut hole, so a hook silently stops at that boundary), and writing `:scope` explicitly DOES add (0,1,0).<br>*Measured, single engine:* proximity beat source order in both directions; a layered `@scope (.inner)` LOST to an unlayered `@scope (.outer)` despite being nearer. One of the two results most likely to differ in Firefox/WebKit, neither installed. | `@scope` reads like the tool for "component styling that doesn't leak" and solves a different problem — proximity disambiguation — from the one at hand, an outside consumer needing to win. | `@scope` appearing in a diff whose stated purpose is overridability or containment is the finding. | SHOULD |

## Accessibility

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| CSS-A11Y-01 | `forced-colors: active` sits above everything else in this rule set. The UA replaces `color`, `background-color`, `border-color` and `outline-color` with system colours regardless of layer, specificity, origin or `!important` — including a value arriving through `var()`. Two consequences the spec summary hides: `box-shadow` and `background-image` are SUPPRESSED to `none`, not recoloured; and SVG `fill`/`stroke` is not touched at all, so an icon keeps its authored colour and can vanish against the forced background. Give icons an explicit `fill: CanvasText`. `forced-color-adjust: none` is the only opt-out and it opts the whole subtree out of the user's palette — an accessibility decision, not a styling escape.<br>*Measured, single engine:* 30 assertions via Playwright's real forced-colors mode. Author `!important`, a layered `!important` and a `var()`-sourced value were all replaced; `box-shadow` and `background-image` computed `none`; SVG `fill` stayed at its authored value. | The one cascade mechanism above the entire token contract, and an accessibility obligation rather than a nicety. The SVG gap is a real defect, not a spec restatement. | Run the page under a forced-colors context (Playwright `newContext({forcedColors:'active'})` drives the real mode, not a mock) and read `getComputedStyle` on: one text element, one element whose colour arrives via `var()`, one with `!important`, one inside a layer, one `box-shadow`, and every inline SVG icon. Any `forced-color-adjust: none` in the tree needs a comment naming the accessibility trade. | MUST |

## Custom Properties

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| CSS-VAR-01 | `var(--x, fallback)` uses the fallback only when `--x` is NOT SET. A property that IS set, to a value the consuming declaration cannot use, is invalid at computed-value time: it resets to the inherited value on an inherited property and to the initial value on a non-inherited one, and ignores the fallback entirely. An empty custom property (`--e: ;`) is a valid value and likewise skips the fallback. So a hook's fallback chain does not protect you from a consumer who sets the hook to the wrong type. `@property` with `initial-value` is the fix — and it MUST declare `syntax` and `inherits`, and `initial-value` unless `syntax:"*"`, or the whole rule is silently discarded with no error.<br>*Measured:* missing → fallback; invalid on an inherited property → the parent's colour, not the fallback; empty custom property → IACVT, no fallback. With `@property`, an invalid value fell to `initial-value`; `inherits:false` stopped descendants seeing the ancestor value; a registered `<length>` interpolated while the unregistered control jumped. | The hook pattern's entire safety story is the fallback, and the fallback does not cover the most likely consumer mistake. | For every published hook whose fallback is load-bearing there is a matching `@property` registration. Set the hook to a deliberately wrong type in a scratch page and confirm the element renders the fallback rather than the inherited value. If you transition a custom property, register it — and transition the property itself, not a derived native property, or the test lies. | MUST |

## The Public API

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| CSS-API-01 | Where a compiler generates the target name, that name is not an API. Vue's `data-v-<hash>` rotates per build; Svelte's hash is a function of the FILENAME, so moving a file rotates every hash it emits; a CSS Modules hash is path-derived and its whole SHAPE changes with the bundler; styled-components' `sc-` id shifts when an unrelated `styled()` call executes first; vanilla-extract and StyleX hash by default, including the LAYER name. Ship a dedicated `data-*` identity attribute instead, kept off the `class` attribute — and remember it carries exactly class specificity, so it is not an override mechanism by itself. **Except where nothing generates a name**: plain CSS, Tailwind (utility names ARE the public contract), and a VS Code webview already have a stable target.<br>*Measured:* swapping which of two sibling `styled.div` calls executes first flipped one component's id and class entirely; the CSS Modules hash shape differs by bundler; `layer('components')` emitted `@layer uan7er0`. | Two independently-built repos converged on the identity-attribute shape. But generalising it into a universal MUST mandates a parallel identity layer in three surfaces where the author's own class names are already build-invariant public API. | Pick one convention and grep for it — `grep -rn 'data-slot=' src` if you adopted shadcn's, your own otherwise. Every published hook must be reachable from an element carrying one. Then grep your own tests, docs and README for a literal generated hash; each hit is a break waiting for the next file rename or bundler change. | SHOULD |
| CSS-API-02 | A component hook is override-only. Grammar `--<namespace>-<component>-<property>`, never declared by your own styles, always read with a `var()` fallback to the semantic tier: `border-radius: var(--ns-card-radius, var(--ns-radius-lg))`. Three ways to get it wrong: a hook that STORES a value becomes a second source of truth that stops tracking a rebrand — and that is exactly what mainstream token tooling emits by default; a bare property-name hook leaks into every component reading that property; and a name your build rewrites or hashes is not a public name at all.<br>*Measured:* Angular 22.1.4 rewrites every component custom property unless authored `--global--name`; vanilla-extract token names hashed and were still beaten by a consumer `:root` override; Lit's `:host`-declared hook reached an internal `var()` fallback chain across the boundary. | This resolves the apparent contradiction with "never expose a component-level colour knob": the ban is on an independent second value, not on a fallback override point. Every major design system ships the fallback shape; the failure is shipping the stored shape, or a name the compiler renames. | For every published hook, grep source for its literal name — `grep -rn -- '--acme-card-radius' src` — and confirm only `var()` READ sites come back, never a declaration. Then grep the BUILT artifact for the same literal name: absent, or present hashed, means the published name is not the shipped name. On Angular, grep the artifact for `%NS%` instead, or assert against live computed styles. | SHOULD |

## The Gate

| ID | Rule | Rationale | Verification | Severity |
|---|---|---|---|---|
| CSS-GATE-01 | The gate reads the BUILT artifact, in an engine that can actually represent the feature — and it is routed per framework or it passes with zero coverage. Four ways it is faked. (1) Wrong artifact: Angular compiles component `styles:` into the JS bundle; Qwik's built JS chunk holds the RAW unscoped author CSS; Svelte publishes uncompiled `.svelte`; Astro's view-transition layer lands in an inline `<style>`. A glob that matches nothing passes silently. (2) A regex where minification defeats it — production CSS is one physical line. (3) A DOM emulator: **no DOM emulator may ever test a layered cascade** — not "with caution", not "works for simple cases". (4) It was never watched go red.<br>*Measured:* happy-dom 20.12.0 has zero `@layer` support and a bare layer statement corrupts every rule after it; jsdom 30.0.1 parses `@layer` correctly and applies none of it. `wc -l` = 1 on both production bundles measured. | Both source repos found that stripping one component's layer wrapper left every OTHER assertion green — the build succeeded, every token test passed — and only the dedicated built-output check caught it. | For each check: name the artifact and confirm the path exists after a real production build, discovering it with `find` and failing on an empty match; confirm it is not a regex over minified text; confirm any cascade assertion runs in a real browser engine. Then run it against a deliberately broken copy. A pass on the broken copy is the violation. Routing table in [gate.md](gate.md). | MUST |
| CSS-GATE-02 | A verification enters this rule set, a CI job, or a review only after it has been watched go red against a deliberately planted violation. A cascade harness needs at least one deliberately-inverted expectation and one dead-selector control, and every rule's identity must be encoded in the observed value (`rgb(1,0,0)` vs `rgb(2,0,0)`) so a "pass" cannot come from reading a UA default.<br>*Measured:* two independent harnesses built for this rule set shipped false results before their controls caught them, and both read as clean passes. | A check that cannot fail launders an unchecked change as a checked one, and reads exactly like a passing one forever. | Copy the subject, break the thing the rule forbids, run the verification. A pass on the broken copy is the violation. For a browser harness specifically: open a FRESH page per case — `page.setContent()` reuses one window, so a `customElements.define()` in case 1 silently supplies the CSS for every later case. | MUST |

## The three code blocks

```css
/* wrong — the fallback does not cover a consumer who sets the wrong type */
.card { border-radius: var(--ns-card-radius, var(--ns-radius-lg)); }

/* right — registration makes the fallback actually hold, and makes it animatable */
@property --ns-card-radius { syntax: "<length>"; inherits: false; initial-value: 0px; }
```

```css
/* wrong — inside a shadow component this locks every consumer out permanently */
:host { color: var(--x, red) !important; }

/* right — no !important at all; the consumer already wins by Context */
:host { color: var(--x, red); }
```

```css
/* wrong — an icon keeps its authored fill under forced-colors and can vanish */
.icon { fill: var(--ns-fg); }

/* right */
.icon { fill: var(--ns-fg); }
@media (forced-colors: active) { .icon { fill: CanvasText; } }
```
